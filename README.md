# Talent Finder — Recruiter Portal (Frontend)

React single-page app for a multi-tenant recruitment workspace. A recruiter selects a tenant,
manages candidates and job orders, sees candidates **ranked by matched required skills**, and
shortlists them in one click.

Backend API: [`talent_finder_backend`](https://github.com/sunabh07/talent_finder_backend)

---

## Stack

React 18 · Vite · TypeScript · Tailwind CSS · Redux Toolkit + **RTK Query** · lucide-react

Redux is named in the assignment. RTK Query additionally supplies caching, loading/error states
and tag-based invalidation — which is what makes "switching tenants never shows stale data" a
property of the data layer rather than a refetch call on every screen.



## Screens

| Route | Screen |
|---|---|
| `/tenants` | Tenant list + create dialog |
| `/candidates` | Candidate list — search, sort, pagination, `⋮` View/Edit/Delete |
| `/candidates/new`, `/candidates/:id/edit` | Add / edit form with optional CV upload |
| `/candidates/:id` | Profile, skills, CV download, shortlist history |
| `/job-orders` | Job order list with all seven required columns |
| `/job-orders/new`, `/job-orders/:id/edit` | Add / edit form (no file upload, per the brief) |
| `/job-orders/:id` | **Ranked matching candidates + one-click Shortlist + shortlisted section** |
| `/submissions` | Job Order, Candidate, Status with search, sort, pagination |

Layout is fixed by the assignment: left sidebar (Tenant, Candidate, Job Order, Submission), top
header with logo left and bell + avatar right, tenant dropdown in the page header. The avatar and
bell are explicitly demo-only — this build has no authentication.

## Structure

```
src/
  app/          store · api (RTK Query) · tenantSlice · hooks · useListControls
  components/   ui · DataTable · Layout · TenantSwitcher · SkillInput
  features/     tenants/ · candidates/ · jobOrders/ · submissions/
  types.ts      mirrors the backend response schemas
```

UI primitives are hand-written rather than generated by the shadcn CLI: this project needs about
eight of them, and the generator would add a config, a utils module, Radix peer dependencies and
~30 files that go unused. `DataTable.tsx` holds the list-page anatomy the assignment's reference
wireframe fixes — summary cards, toolbar, action menu, table, footer, pagination — so the four
modules cannot drift into four different-looking screens.

## Two things worth reading the code for

**The tenant header is attached once.** `prepareHeaders` in `app/api.ts` reads the selected
tenant from Redux and sets `X-Tenant-ID` on every request. No component ever passes a tenant id
by hand. This mirrors the backend's single `get_tenant_scope` dependency: one place to get right
on each side of the wire.

**One Shortlist click updates four screens with no manual refetch.** The mutation declares
`invalidatesTags: ["JobOrder", "Submission", "Candidate"]`, which refreshes the match row's
button, the job's Shortlisted Candidates section, the Submission List and the candidate's own
detail page. No screen knows the others exist — the Submission List is not even mounted when the
click happens.

Switching tenants invalidates the three tenant-scoped tags, and list screens key their skeleton
off `isFetching` rather than `isLoading`, so a switch shows loading and then the new tenant's
data — never the previous tenant's rows.

## Known limitations

- **No frontend test suite.** The backend carries 139 tests; UI verification was manual in the
  browser. Vitest + Testing Library would be the addition.
- **No authentication.** The tenant selector is a demo context switch; the backend validates the
  header but cannot verify who sent it.
- **CV auto-fill is not implemented.** Optional in the brief, which states twice that manual
  entry scores the same. The upload control stores the file and says so plainly.
- **The tenant switcher loads up to 100 tenants in one request.** Fine for a demo; a real
  deployment needs a searchable async picker.
- **No optimistic updates.** Mutations wait for the server round trip.
